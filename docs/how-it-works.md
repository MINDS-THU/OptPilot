# How a Run works

Discovery resolves the manifest and stores content-addressed artifact definitions and source blobs in `.optpilot/experiments`. Editing a definition or one of its dependencies creates a new version. Review resolves artifact IDs to exact immutable versions, validates compatibility and records the selected runner, metric, budget and planned Trials. Admission is idempotent for a Run ID and schedules its fixed Candidates over the selected Instances and repetitions. Execution records inputs as used only when work reaches a worker.

After the baseline or prior generated batch completes, the Generator receives only successful Trial scores named by each Task's `feedbackMetrics`, along with public contracts, seed, budget and a temporary workspace. It does not receive private grading values or grader evidence. Returned submissions are validated, frozen and scheduled. Generation records preserve the input feedback, output versions, logs and failure state. Cancellation, waiting for resources, worker loss and grading failure remain distinct. Repeating a frozen Study with a new Run ID creates a new Run; resuming a Run retains its identity and does not rescore completed Trials.

Native Python Trials run in separate local worker processes with timeout, retry and cancellation handling. The code is trusted and can access host resources; this process boundary is not a hostile-code sandbox. A reviewed Study can instead use a registered POSIX SSH target for native grading. The controller and optional Generator remain local while a remote worker receives frozen inputs and keeps a recoverable job receipt. Manual Tasks wait for a named operator to claim and submit a receipt-backed measurement.

For Harbor, Core stages frozen task packages and candidate configurations, starts a local Harbor job through Docker, and reconciles its actual terminal Trial records. Harbor controls its own task sandbox and agent authentication. Scores with missing metrics, agent exceptions or invalid rewards do not become valid zeros. External result imports also require a reviewed Study and explicit version bindings, preserve partial coverage, and never claim OptPilot executed imported work.

Resource requirements are frozen with artifact versions. Before launch, the resource planner checks registered capacity, consumables and quotas against Study budgets. Reservations and usage receipts use a shared local registry. A Run may wait for missing resources or a required measurement, then resume with the same Run ID.
